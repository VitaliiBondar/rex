# REX — CRM відділу рекрутингу

Веб-CRM для команди рекрутерів: ведення кандидатів, статуси-конвеєр, помісячна
статистика, канбан. Ролі ADMIN/RECRUITER. UI українською.

## Стек
- Next.js 16 (App Router) + React 19 + TypeScript, Tailwind v4
- Prisma 7 (driver adapter `better-sqlite3`) → SQLite локально; для продакшену — Postgres
- Auth.js v5 (credentials, JWT), split-config: `src/auth.config.ts` (edge) + `src/auth.ts` (Node)
- Recharts (графіки), dnd-kit (канбан), react-hook-form + Zod (форми/валідація)

## Команди
- `npm run dev` — розробка (http://localhost:3000)
- `npm run db:seed` — заповнити демо-даними (перезаписує БД)
- `npm run import:historical` — одноразовий імпорт історичних кандидатів напряму в БД
  (див. розділ "Одноразовий імпорт історичних кандидатів" нижче)
- `npm test` — юніт-тести (логіка статистики)
- `npx prisma migrate dev` — міграції

## Демо-акаунти (після seed)
- Адмін: `admin@rex.local` / `admin123` (дефолт для локальної розробки)
- Рекрутер: `recruiter@rex.local` / `recruiter123` (дефолт для локальної розробки)
- Паролі перевизначаються через `SEED_ADMIN_PASSWORD` / `SEED_RECRUITER_PASSWORD` у `.env`
  (див. `.env.example`) — обов'язково перед seed на будь-якій недовірчій/продакшн базі.

## Ключові місця
- Доменні enum-и + лейбли/кольори: `src/lib/domain.ts` (єдине джерело правди)
- Чиста логіка статистики (тестована): `src/lib/stats.ts` + `stats.test.ts`
- Server actions: `src/lib/actions/*`
- Запити до БД: `src/lib/queries.ts`
- Захист маршрутів і ролей: `src/middleware.ts` + `callbacks.authorized` в `auth.config.ts`

## Конвеєр статусів
Активні етапи (4): `UNIT_SEARCH` (Пошук підрозділу, дефолт при створенні) →
`COLLECTING_DOCS` (Збір документів) → `MEDICAL_COMMISSION` (Проходить ВЛК) →
`CONTRACT_SIGNING` (Оформлення). Фінальні (з будь-якого активного етапу):
`ENLISTED` (Зараховано), `REJECTED_BY_US`, `SELF_WITHDREW`. Немає окремого
поля "відповідальний рекрутер" — усі бачать і редагують усіх кандидатів.
На канбані (`board-client.tsx`) `REJECTED_BY_US`/`SELF_WITHDREW` візуально
об'єднані в одну колонку "Відмови" (з пікером причини при drag&drop), але в
даних/статистиці лишаються окремими статусами.

Перехід з `UNIT_SEARCH` у будь-який статус, крім відмов, вимагає вказаного
`unitId` (`requiresUnitAssignment` у `domain.ts`). Перевірка — виключно
на сервері, в `changeCandidateStatus` (`lib/actions/candidates.ts`); при
порушенні дія повертає `{ ok: false, code: "NEEDS_UNIT" }` замість запису
в БД. Усі три поверхні зміни статусу (канбан, `StatusSelect` у списку й на
сторінці кандидата) реагують на цей код спільною модалкою
`components/require-unit-modal.tsx` — жодна з них правило не дублює.

## Помісячний перегляд кандидатів
`/candidates` за замовчуванням показує ПОТОЧНИЙ місяць; навігація ‹ › (`month-nav.tsx`)
гортає історію. `lib/stats.ts::candidatesForMonth` реконструює історичний статус
кандидата на вибраний місяць (не живий поточний) і коректно ховає тих, хто
фіналізувався РАНІШЕ цього місяця. Зміна статусу (`StatusSelect`) дозволена лише
в поточному місяці; при перегляді минулого — статичний `StatusBadge` (read-only).
Колонка "Дата зарахування" (`enlistedDate`) завжди показує факт, незалежно від
переглянутого місяця.

Поруч із перемикачем місяця — лічильник "Показано кандидатів: N", що завжди
відображає точну кількість рядків у поточному відфільтрованому й відсортованому
списку (реагує на всі фільтри, а не фіксоване число). Кнопка "Весь період"
(`month=all` у query-параметрі `month`, `month-nav.tsx`) показує всіх кандидатів
одразу з їхнім живим поточним статусом (без історичної реконструкції за
`candidatesForMonth`) — редагування статусу (`StatusSelect`) дозволене й тут,
так само як у поточному місяці. Заголовки колонок Кандидат/Підрозділ/Дата
зарахування/Статус клікабельні (`sort`/`dir` у query-параметрах,
`candidate-list.tsx`): сортування за статусом іде в порядку конвеєра
(`STATUSES` з `domain.ts`), не абетково за кодом; кандидати без підрозділу чи
без дати зарахування завжди залишаються в кінці списку, незалежно від напрямку
сортування. Кнопка "Скинути" у `filters.tsx` скидає лише фільтри (пошук/статус/
тип/канал), зберігаючи вибраний місяць і сортування.

## Одноразовий імпорт історичних кандидатів
Форма створення кандидата завжди ставить статус `UNIT_SEARCH` і поточну дату —
через UI немає способу додати кандидата "заднім числом". Для цього є
`scripts/import-historical-candidates.ts` (`npm run import:historical`): читає
JSON-масив із `scripts/historical-candidates.data.json` (шлях можна передати
аргументом) і для кожного запису створює кандидата й повний ланцюжок
`StatusChange` (Пошук підрозділу → Збір документів → ВЛК → Оформлення →
Зараховано) з датами, рівномірно розподіленими між датою старту
(`pipelineStartDate`, або `enlistedDate` мінус 45 днів за замовчуванням) і
фактичною датою зарахування — це потрібно, щоб `lib/stats.ts` показував
кандидата на правдоподібному проміжному етапі за минулі місяці, а не одразу
фінальний статус. Автор історичних змін (`changedById`) — користувач
`admin@rex.local`, знаходиться за email під час виконання (не хардкодиться
`id`, бо `cuid()` недетермінований). Файл із самими даними
(`historical-candidates.data.json`) містить ПІБ реальних людей і додано в
`.gitignore` — ніколи не комітиться, на відміну від коду самого скрипта.

## Примітки
- enum-поля БД зберігаються рядками (сумісність SQLite/Postgres); валідні значення — у `domain.ts`.
- Статистика «за місяць»: додавання рахується за `createdAt`, зарахування/відмови — за датою
  переходу в статус (`StatusChange.changedAt`), що коректно обробляє перенос кандидатів між місяцями.
- `middleware` конвенція має deprecation-попередження в Next 16 (радять `proxy`) — працює, замінити згодом.
- Сесія (JWT) прив'язана до домену (`localhost:3000`), а не до конкретного процесу/БД. Якщо
  `dev.db` перестворити (новий seed, інший worktree з власною базою) без виходу з акаунта в
  браузері, стара кука вказує на неіснуючого `User.id` — будь-яка дія, що пише `changedById`
  (напр. `changeCandidateStatus`), впаде з `PrismaClientKnownRequestError: Foreign key constraint
  violated`. Це не баг у коді — ліки: вийти з акаунта і зайти знову.
- Feature-гілки розробляються в `.worktrees/<назва>/` (git worktree, ігнорується в `.gitignore`);
  `vitest.config.ts` явно виключає `**/.worktrees/**`, інакше `npm test` з головного каталогу
  дублює всі тести з активних worktree.
- У робочій директорії станом на 2026-07-30 є НЕЗАКОМІЧЕНІ зміни з двох різних, не пов'язаних
  між собою джерел: (1) доробки `/candidates` (лічильник "Показано кандидатів", "Весь період",
  сортування колонок) і скрипт історичного імпорту — зроблені разом з Claude, комітити поки що
  свідомо не просили; (2) окремий, вже наявний до цього UI-рефакторинг (прибирання пропу
  `eyebrow` з `PageHeader` і супутні зміни в `board-client.tsx`, `board/page.tsx`,
  `dashboard/page.tsx`, `settings/page.tsx`, `page-header.tsx`, `button.tsx`, `card.tsx`,
  `modal.tsx`, `globals.css`) — це чужа/попередня робота, Claude її не торкався. Перед комітом
  варто уточнити в користувача, що саме коммітити — не змішувати ці дві групи змін автоматично.
